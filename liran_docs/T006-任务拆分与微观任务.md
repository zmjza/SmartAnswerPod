## 问题与修复表

| 大白话的问题 | 大白话的问题描述 | 解决方法 |
| --- | --- | --- |
| 双并发第二个浏览器卡空白 | 首次登录文档导航可能长时间不 commit，旧逻辑直接等待 `goto`，空白恢复 gate 没有机会观察到；第二实例看起来 100～200 秒无反应 | `electron/noqr/session.ts` 改为可观察的 commit 导航和空白 gate，首次失败/延迟提交时按活动请求和刷新预算恢复；答题页仍禁止刷新。新增 T006-NAV01/NAV02。已复测通过 |
| 下一轮账号一直排队 | 排队任务只靠自己每 400ms 调 `acquire()`，槽位释放后没有中央唤醒，异常/关闭路径可能长期不流转 | `electron/pool.ts` 增加释放通知，`electron/noqr/run.ts` 中央唤醒排队等待；400ms 只保留兜底。已用 3 账号并发 2、正常/失败/停止/排队停止和真实 R02 验证 |
| 队列顺序可能被旧历史污染 | `SlotPool` 用 Map 首次插入顺序扫描，账号重新入队时可能沿用旧位置，不是本轮 FIFO | `electron/core/slot-pool.ts` 增加单调入队票号，`promoteQueued()` 按本轮票号取最小；p0 Q01b 覆盖旧顺序污染 |
| 浏览器关闭前就释放容量 | `release()` 先标 released 再 `context.close()`，慢关闭时下一名可能提前启动，真实浏览器数瞬时超限 | 新增 `closing` 状态并继续占用容量；关闭完成或 30 秒安全上限后才释放和补位，释放返回真实的容量变化。已通过 build、P0 和真实 R01/R02 |
| 停止后排队账号晚到启动 | `acquire()` 在停止信号发出后才成功返回时，旧代码仍可能进入 `runOne` | 获取结果返回后立即检查 AbortSignal，已停止则不进入登录/答题并释放上下文；t006-scheduler 的排队停止场景通过 |
| 旧批次仍在运行时新批次不能选课 | 选课 token 在等待结束时被删除，`pendingSelected` 又把已开始账号算作扫描中，第三名被误报阻塞 | token 保留到本轮任务 finally，`pendingSelected` 排除已批准开始的账号；新增 selected 旧批次阻塞场景通过 |
| 释放通知可能重复 | 启动失败和任务 finally 都调用 release，旧路径可能重复通知补位 | `SlotPool.release()` 返回是否发生真实状态变化，只有变化时通知；启动失败、关闭、finally 重复调用幂等 |
| 真实测试无法证明多账号完整链 | 旧 harness 的 score 只允许单 alias，只能证明并发登录，不能证明并发作答/交卷/取分和排队完整流转 | 新增 `score-concurrent` 测试阶段，允许多 alias、账号并发 2 和 stop-after-score-round；最终用于 3 账号完整链路 |
| 同学生可能重复启动 | 同一学生并发调用 `acquire()` 时，第二次可能在第一次仍处于启动中时再次启动同一 profile，失败后还会误释放另一个启动的槽位 | 对同一学生启动链做串行合流，重复调用复用当前启动结果；释放使用 epoch 校验，避免晚到结果覆盖新状态 |
| 慢请求被误认为心跳 | 同一路径的慢请求可能被重复活动抑制器当成心跳，60 秒宽限后被错误刷新 | 同 method/path/query/resourceType 的前两次视为业务活动，第三次以上才按心跳处理；超过 1.5 秒的慢请求升级为业务活动 |
| 点击作答期间课程页被刷新 | 已点击“开始作答”但答题文档尚未完成导航时，外层课程页可能按空白规则刷新，导致入口状态被破坏 | 点击后建立导航意图锁，答题文档导航完成前禁止刷新课程页；导航失败后再按有界规则恢复 |
| 未知非空页面无限占槽 | 页面既不是空白也没有已知业务标记时，旧逻辑可能不断等待，账号一直占用并发名额 | 将 unknown 非空页纳入有界恢复预算；超出预算安全停止当前学生并释放槽位 |
| 浏览器上下文关闭不触发任务停止 | 上下文被外部关闭后，运行任务可能仍等待页面操作，导致队列补位永远不触发 | 浏览器上下文 close 事件向对应学生发出 abort；运行链最终 finally 统一释放槽位并补位 |
| 普通答题错误被误报为页面中断 | 已有进度时发生 AI、选项或业务读取错误，旧逻辑仍无条件包装成 `answer_interrupted`，账号可能停在需人工处理 | 只有连续两次观察确认答题面异常才升级页面中断；普通业务错误只隔离当前课程/作业并释放账号槽位 |
| 释放后仍残留排队标记 | 槽位已是 released，但学生状态仍可能是 `queued=true`，造成 UI 和调度判据不一致 | 任务 finally 同时清理 `queued=false`；harness 汇总和门禁独立断言最终 queued 为 0 |
| 关闭超时没有确认物理退出 | 逻辑槽位在上下文关闭超时后可能已释放，但旧浏览器进程仍存活，实际并发可能超过配置 | 关闭任务进入 `closing` 并继续占容量；超时后终止进程树并确认无相关 profile 进程后才允许补位 |
| 零浏览器峰值也能通过 | 并发门禁只检查峰值不超过配置，没有检查是否真的达到配置峰值 | 门禁同时要求峰值等于配置值、不得超过配置值，并分别检查槽位、浏览器和活动上下文计数 |
| 课程并发只测了通用调度器 | 旧测试只证明 `mapWithConcurrency` 能并发，不能证明无码课程生产链路真的并发 | 新增无码课程页活动峰值监控和生产接线测试，按配置 2/3/4/5/6/8 检查达到峰值、保持上限和结束回落 |
| 设置页并发仍写 Max 6 | 设置实际允许课程并发 8，但提示文案仍显示 Max 6，用户会误判上限 | 文案改为 Max 8，并纳入 UI E3 断言 |
| 8 并发选择学生按钮超时 | 8 个账号时“更多学生”弹层点击存在时序问题，测试无法稳定选择第 9 个账号 | harness 增加强制点击和页面内点击回退；该问题先归因测试编排，再复跑确认产品补位 |
| 8 并发业务结束后进程不退出 | 9 个账号都已显示 stopped/released，日志也记录浏览器和活动上下文归零，但旧轮次超过 4 分钟不再写日志且未退出，只能人工中断 | 已修复并完成 v9 复测：`account-parallel-8-085045.log` exit 0，峰值 8、queued 补位、最终 queue/browser/context 0；历史不退出日志保留 |
